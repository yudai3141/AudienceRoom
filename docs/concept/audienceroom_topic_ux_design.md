# AudienceRoom: トピック記憶型体験の UX 設計

`audienceroom_concept_ux_spec.md`（コンセプト/要件）を、画面・フロー・フロントエンド実装方針に落とした設計書。
DB 側の対応は `backend/docs/db-schema-plan-b-topics.md` を参照。

> この設計は議論を経て、(1) 面接の質問は永続せず**仮想 GraphRAG で都度生成**、(2) **自己評価の数値入力は取らず**客観結果の提示で内的比較に委ねる、(3) ペルソナ活用は後続、という方針に更新済み。

---

## 0. 設計の出発点

現行アプリは「セッション単位（1 練習で完結）」の体験になっている。新コンセプトの核は、その上に **トピック（育てるエピソード）という縦糸**を通すこと。

| 軸 | 単位 | 揮発性 | UI 上の見え方 |
| --- | --- | --- | --- |
| 練習 | `practice_session` | 1 回で完結 | 面接ルーム / その回のフィードバック |
| 記憶 | `topic` | 練習をまたいで蓄積 | ダッシュボード / トピック詳細（育っていく） |

ユーザの主導線を「セッションを始める」から **「トピックを育てる」** に変える。ホーム = トピックダッシュボードにする。

---

## 1. 体験フロー全体図

```
[ホーム = トピック一覧]
   │  ・育てているトピックがカードで並ぶ
   │  ・各カードに 完成度 / 弱い論点数 / 次の質問
   ▼
[トピック詳細]  ←──────────────┐
   │  ・木/グラフで「埋まっている所/空いている所/矛盾」     │
   │  ・話せること / 弱いこと / 深掘りされそうな所           │
   │  ・[このトピックで練習する]                           │
   ▼                                                      │
[練習セットアップ]                                          │
   │  ・トピック選択（既存 or 新規）                        │
   │  ・モード/面接官など既存設定                            │
   ▼                                                      │
[面接ルーム]  ← 仮想 GraphRAG ループ                        │
   │  ・AI がグラフの弱点/矛盾ノードを選んで深掘り           │
   │  ・回答するたびグラフが更新（裏側）                     │
   ▼                                                      │
[フィードバック]                                            │
   │  1. 今回話せたこと                                     │
   │  2. まだ弱いところ                                     │
   │  3. 想定される追加深掘り質問                            │
   │  4. 客観的に見た結果（answered 5/6、崩壊は1論点 等）     │
   │  ・[トピックがこう更新されました] 差分表示              │
   └──────────────────────────────────────────────────────┘
```

> 当初案にあった「自己評価入力」ステップは廃止。ズレはシステムが数値で示すのではなく、ブロック4の**客観的な分解提示**でユーザが自分の内的イメージと比較できるようにする。

## 2. 画面別仕様

### 2.1 トピック一覧（ホーム / ダッシュボード）

**目的**: 「自分のエピソードが育っているか」を一目で。スコア羅列ではなく**成長の地図**。

各トピックカードに表示（`audienceroom_concept_ux_spec.md` 6.1）:
- トピック名
- 練習回数 / 最終練習日（`practice_sessions.topic_id` から導出）
- 完成度（プログレスバー + %）← `topics.completeness_score`
- まだ弱い論点の数 ← `topic_nodes.coverage IN ('weak','gap')` の件数
- 次に練習すべき質問（1 件）← 仮想 GraphRAG で生成（直近生成分のキャッシュ可）

```text
┌─ 研究内容 ──────────────────────┐
│ 完成度 ███████░░░ 65%            │
│ 練習 4回 ・ 最終 6/20            │
│ 弱い論点 3個                    │
│ 次の練習: 評価方法と自分の貢献   │
│              [練習する] [詳細]   │
└─────────────────────────────────┘
```

- 上部に `[+ 新しいトピック]`。
- 完成度が上がったトピックを軽く強調（「前回より +12%」など）して成長実感を出す。

### 2.2 トピック詳細

**目的**: トピック内が**構造として**見える。文章の羅列にしない（spec 6.2 / 6.3）。

構成（上から）:
1. **完成度ヘッダ** — 完成度 % + 一言サマリ（`current_summary`）。
2. **木/グラフ可視化** — `topic_nodes` + `topic_edges` を描画。ノードを `coverage` で塗り分け:
   - `covered` = 緑（話せる）
   - `weak` = 黄（説明が弱い）
   - `gap` = グレー破線（まだ空いている）
   - `relation_type='contradicts'` のエッジは赤系で「ここに食い違い」を強調 → 練習の的になる。
3. **3 カラムのカード** — 「話せるようになったこと / まだ弱いこと / 深掘りされそうなこと」。各カードはノードへリンク。
4. **次回練習すべきこと** — 仮想 GraphRAG で生成した次の質問。
5. `[このトピックで練習する]` CTA。

```text
研究内容（完成度 65%）
├── 研究テーマ      ● PTSD患者モデル          [covered]
├── 問題意識
│   ├── 既存モデルでは連想構造を扱いにくい    [covered]
│   └── 主観的な記憶変化を表現したい          [weak]
├── 手法
│   ├── エピソード記憶                        [covered]
│   └── グラフDBによるエンティティ連想        [covered]
├── 強み
│   └── 設計意図は説明できている              [covered]
└── 弱み
    ├── 評価方法が曖昧                        [gap]
    ├── 自分の実装貢献が曖昧                  [weak]
    └── 企業との接続が薄い                    [gap]
   ⚡ 矛盾: 「主導した」↔「チームで決めた」（contradicts）
```

> 可視化は MVP では軽量に。まずはインデント付きツリー（HTML/CSS）で `coverage` を塗り分け、`contradicts` を強調するだけでも価値が出る。本格的なノードリンク図（React Flow 等）は後続の任意拡張。

### 2.3 練習セットアップ（トピック選択を追加）

既存のセットアップフォームの**先頭にトピック選択ステップ**を足す:
1. 既存トピックを選ぶ（過去情報＝グラフが引き継がれる）/ 新規トピックを作る
2. 既存のモード・面接官・テーマ等の設定
3. 開始

トピックを選んだ時点で「前回ここまで話せています。今日は『評価方法』を深掘りします」と**今日の狙い**を提示し、「覚えてくれている」感を最初に作る。

### 2.4 面接ルーム（仮想 GraphRAG ループ）

会話 UI 自体は現行を踏襲。差分は裏側のループ（詳細は DB 設計書「仮想 GraphRAG」参照）:

```
[候補抽出] coverage=weak/gap・矛盾を持つノードを SQL で数件
   ↓ 近傍グラフ + ペルソナ + 直近の会話履歴 を context に
[選択+質問] LLM が流れを踏まえてノードを選び深掘り質問を生成
   ↓ ユーザ回答
[抽出+更新] 回答からグラフ差分を抽出 → 補強 / 新規 / 矛盾(contradicts) を upsert
```

- UI 変更は最小（裏でグラフが育つ）。
- (任意 / 後続) 各 AI 質問に「i」アイコン → 「なぜこの質問か」（選ばれたノードが弱い/矛盾しているから）を後から開ける。

### 2.5 フィードバック画面（4 ブロック + トピック更新差分）

`audienceroom_concept_ux_spec.md` 5.6 の 4 項目を**この順で**:

1. **今回話せたこと**（`positive_points`）— ポジティブから始める。
2. **まだ弱いところ**（`improvement_points`）— 「全部ダメ」ではなく限定された論点として。
3. **想定される追加深掘り質問** — 仮想 GraphRAG で生成（永続しない）。
4. **客観的に見た結果**（最重要ブロック）:
   ```text
   答えられた質問   5 / 6
   崩壊していた論点  1つだけ（評価方法）
   伝わっていたこと  研究概要・設計意図

   今回は「評価方法」と「自分の貢献」に改善が集中しています。
   全体が崩れていたわけではありません。
   ```
   - **自己採点との差分は数値で明示しない**。客観的な分解（answered N/M、崩壊は1論点、等）を提示し、ユーザが自分の内的イメージ（「全部ダメだった」）と**自分で**照らせるようにする（spec 6.4 の目的＝過小評価の癖への気づき、を friction 少なく実現）。

最後に **「このトピックがこう更新されました」** の差分:
```text
✓ 「グラフDBを使う理由」が 弱い → 話せる に更新
+ 新しい弱点「評価方法」を検出
⚡ 「主導した」と「チームで決めた」の食い違いを記録
→ 次の練習: 評価方法 / 自分の貢献
                          [トピック詳細を見る]
```
これが「育っている」実感の締め。

## 3. フロントエンド実装方針（CLAUDE.md 準拠）

### ディレクトリ
```
frontend/src/
  app/
    topics/                # ルーティングのみ
      page.tsx             # 一覧
      [topicId]/page.tsx   # 詳細
    sessions/[id]/
      feedback/page.tsx
  features/
    topics/                # トピックのロジック（一覧/詳細/可視化）
    feedback/              # 4ブロック + 客観結果 + 差分
  components/
    topic/                 # TopicCard, TopicGraph, CoverageBadge, ContradictionTag ...
  lib/api/
    topics.ts              # トピック系 API 呼び出し集約
  generated/               # OpenAPI 生成型（手編集禁止）
  hooks/
    useTopics.ts           # React Query 等（Server state）
```

### 状態管理
- トピック一覧/詳細・フィードバックは **Server state** → React Query / SWR。`useState` で抱えない。
- セットアップフォームの入力中だけ UI state。

### フォーム
- 新規トピック作成は **react-hook-form + zod**。API schema（OpenAPI 生成型）と一致させる。loading / error を必ず表示。

### 可視化コンポーネント
- `TopicGraph`: `nodes` + `edges` を受けて `coverage` で塗り分け、`contradicts` を強調。MVP は CSS ツリー、拡張で React Flow。

## 4. API（OpenAPI に追加する想定エンドポイント）

> backend が正本。実装時は ルーター/スキーマ変更 → `openapi.json` 再生成 → `make generate-api` の順（CLAUDE.md 11 章）。

| メソッド | パス | 用途 |
| --- | --- | --- |
| `GET` | `/topics` | トピック一覧（完成度・弱点数・次質問の導出値込み） |
| `POST` | `/topics` | 新規トピック作成 |
| `GET` | `/topics/{id}` | 詳細（nodes / edges / summary） |
| `PATCH` | `/topics/{id}` | タイトル等の更新 |
| `DELETE` | `/topics/{id}` | 論理削除 |
| `POST` | `/sessions` | （既存を拡張）`topic_id` を受け取る |
| `GET` | `/sessions/{id}/feedback` | （既存を拡張）客観結果・想定質問・トピック更新差分を含める |

会話ターンの API（質問生成・回答からのグラフ更新）は既存の会話系エンドポイントを拡張する。ノード選択・質問生成・グラフ更新・coverage 判定・矛盾検出はすべて **service 層**（LLM 呼び出し + SQL）に置き、route には business logic を書かない（CLAUDE.md 5 章）。

## 5. MVP スコープ（最初に出す価値）

`audienceroom_concept_ux_spec.md` 11 章に対応。

### MVP でやる
1. トピックの作成・選択（セットアップにトピック選択を追加）
2. トピックグラフ（nodes + edges）の蓄積
3. 仮想 GraphRAG: AI が弱点/矛盾ノードを選んで深掘り、回答でグラフ更新
4. 練習後にトピック情報（完成度・要約）を更新
5. フィードバック 4 ブロック（客観結果の分解提示を含む）
6. トピック詳細の**ツリー可視化（CSS ベース）**で coverage 塗り分け + 矛盾強調

### MVP でやらない（spec 10 章 + 議論で確定）
- 目線/表情/声の震え/フィラー解析などマルチモーダル
- 本格 GraphDB、pgvector、React Flow 等の高度な可視化
- 質問の永続ワークリスト（都度生成で代替）
- 自己評価の数値入力（客観結果の提示で代替）
- ペルソナの本格活用（Phase B-3 で `user_persona_facts` を組み込む）
- 複数トピック同時練習

## 6. このプロダクトで外してはいけない感覚（実装の北極星）

spec 13 章のユーザ心理を、実装判断の優先順位に翻訳:

1. **「覚えてくれている」** → セットアップ/開始時に過去グラフを必ず提示する。ここが弱いと普通の AI 面接に戻る。
2. **「質問に理由がある」** → 深掘りは弱点/矛盾ノード起点。ランダム質問を出さない（仮想 GraphRAG がこれを保証する）。
3. **「全部ダメではなかった」** → フィードバックは必ず「できたこと」から始め、客観結果を分解提示する。
4. **「次はここを練習すればいい」** → 締めは常に「次の一手」（次に深掘るノード/質問）で終える。

技術的な高度さではなく、この 4 つが UI に出ているかで実装の成否を判断する。
