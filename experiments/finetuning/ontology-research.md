# 研究・制作系ドメイン族 オントロジー v0.2（旧: 研究内容）

> v0.2: **適用トピック（学習ドメイン）**: 研究内容／卒業制作

> v0.1（人間検証 pending-001 のフィードバック反映）:
> 主題ハブ必須化・インサイト→設計判断の leads_to・context 縮小・ノード数上限緩和

学習ドメイン「研究内容」の gold を作るための定義書。SciERC（科学テキストの概念抽出スキーマ）と
CoreSC/DEO（研究談話の修辞構造）を面接用に翻案したもの。**型は共通7型を使い、本書は
「このドメインで何をどの型に入れるか」を定義する**。編集歓迎（v0）。

## 型マッピング

| ドメイン内容 | 型 | 良い label 例 | 悪い label 例 |
| --- | --- | --- | --- |
| 研究テーマ・主題 | concept | 「PTSD対話型エージェント」「若年層向け学習アプリUI改善」 | 「研究テーマ」 |
| ドメイン概念・専門用語 | concept | 「ACT-R理論」「半構造化インタビュー法」 | 「専門知識」 |
| 問題意識・先行研究の限界 | problem | 「トラウマ再喚起リスク」「情報過多による疲労感」 | 「課題」 |
| 限界・未検証な点 | problem | 「サンプル5名の統計的妥当性」 | 「弱み」 |
| 手法・アプローチ・工程 | method | 「グラフDBによる連想記憶」「ユーザーテスト（5名）」 | 「手法」「プロセス」 |
| **自分の貢献・工夫** | component | 「ダッシュボード形式による情報量削減」「スキーマ設計を主導」 | 「改善点」「私の役割」 |
| 成果・評価・数字 | result | 「タスク完了率20%向上・満足度4.5」 | 「効果」「成果」 |
| 学び・獲得スキル | result | 「本質的ニーズを見極める洞察力」 | 「学んだこと」 |
| 応用先・企業との接続 | goal | 「データに基づくUI/UX改善への応用」 | 「将来性」 |
| 研究の場・環境 | context | 「専門学校の卒業制作」「◯◯研究室」 | 「背景」 |

## 必須スロット（欠けたら gap ノードとして立てる）

1. 主題 ≥1（concept）
2. 問題意識 ≥1（problem）
3. 手法 ≥1（method）
4. 成果 or 評価 ≥1（result）— 語られなければ `label: 評価方法（未説明）` のような gap ノード
5. **自分の貢献 ≥1（component）** — 面接で最も突かれる。曖昧なら weak/gap を明示

## 粒度規則

- **主題ノードを必ず立て、グラフのハブにする**。label は会話中の呼び方に忠実に
  （例:「若年層向けスマートフォンアプリのUI改善プロジェクト」）。
- **全ノードはハブから到達可能にする**（part_of は子→親向きのため到達性判定では無向扱い）。孤立サブグラフを作らない。
  遂行中に生じた困難（problem）は `主題 --causes--> problem` で派生させる。
- 束ねノード禁止: 「課題」「改善点」で複数概念を1ノードに圧縮しない。**会話で具体的に
  語られた概念ごと**に分ける。インタビューのインサイト等の列挙も、設計判断に繋がる
  ものは**個別にノード化**する（例: 通知過多／検索性／堅苦しさ／情報過多）。
- context（場・環境）は**深掘りの起点になる場合のみ**（「卒業制作」だけの情報なら省く）。
- 目安 8〜15 ノード、**因果が密な会話では〜20 まで許容**。判断基準は「面接官が深掘りの
  起点にできる単位か」。

- **本人は「自分」と表記**: label/detail で本人を指すときは「自分」（「応募者」と書かない。
  アプリではユーザ自身の脳内グラフとして表示されるため）。
- **相手企業は「志望企業」と表記**（「貴社」と書かない。アプリではユーザ視点のグラフになるため。志望動機アンカーは単に「志望動機」）。
- **エッジも節度**: 同一ターゲットへ並列に多数の leads_to を張らない（代表的な因果に絞る）。
  目安: エッジ数 ≦ ノード数 × 1.3。
- **エッジの忠実性**: 関係は会話中で実際に語られた（または質問→回答の対応で裏付く）因果のみ張る。
  「もっともらしい」だけの補完はしない（例: 課題Aと手法Bが両方あっても、A→Bと語られていなければ繋がない）。

## 典型関係パターン

```
concept(主題)     --addresses--> problem   （プロジェクトが課題領域に取り組む）
concept(主題)     --uses-->      method    （主題ハブから工程の起点へ）
method(調査)      --leads_to-->  problem   （インサイトの発見）
problem(インサイト) --leads_to--> component/method （課題が設計判断・工夫を動機づける）★v0.1
method            --leads_to-->  result    （手法・検証が成果を生む）
method            --leads_to-->  method    （工程チェーン: 実際の因果があるときだけ繋ぐ）
component         --part_of-->   method    （貢献・工夫が工程の一部のとき）
result            --leads_to-->  goal      （成果・学びが応用へ繋がる）
矛盾はすべて contradicts（残す。上書きしない）
```

※ v0.1: 「method addresses problem（解決の向き）」より、**「problem leads_to 設計判断
（動機づけの向き）」を優先**する。addresses は主題レベルの対処に限定。同一ペアに両方向は張らない。

## coverage 判定

- **covered**: 数字・固有名詞・理由まで具体的に語れた
- **weak**: 言及したが曖昧・詰まった・一言だけ
- **gap**: 名前しか出ていない／面接官に聞かれて答えられなかった／必須スロット欠落
- 全ノード covered の gold は原則疑う（詰まりのない面接は稀）
