# 行動経験系ドメイン族 オントロジー v0.2（旧: チーム開発経験）

> v0.2: 単一トピックからドメイン族に一般化。**適用トピック（学習ドメイン）**:
> チーム開発経験／周りを巻き込んだ経験／リーダーシップ経験／困難を乗り越えた経験
> ※ 失敗経験・アルバイトで工夫したことも STAR 型だが **評価用 held-out のため学習に使わない**
> v0.1: research v0.1 と流儀を統一（ハブ必須・到達性・「障害 leads_to 行動」の向き）

学習ドメイン「チーム開発経験」の gold を作るための定義書。行動面接の標準フレーム
**STAR(L)**（Situation / Task / Action / Result / Learning）を概念グラフに翻案。
型は共通7型を使う。編集歓迎（v0）。

## STAR(L) → 型マッピング

| STARL | ドメイン内容 | 型 | 良い label 例 | 悪い label 例 |
| --- | --- | --- | --- | --- |
| S | 状況・チーム構成・場 | context | 「4人チームのハッカソン開発」「文化祭実行委員40名」 | 「状況」「チーム」 |
| T | 目標・ミッション | goal | 「3週間でMVPをリリース」「来場者数を前年比2倍」 | 「目標」 |
| — | **自分の役割** | component | 「バックエンド担当兼進行管理」「意見調整のファシリテータ」 | 「私の役割」 |
| — | 障害・対立・困難 | problem | 「設計方針を巡るメンバー間の対立」「実装の遅延」 | 「困難」「問題」 |
| A | 行動・工夫 | method | 「週次の15分同期MTGを導入」「タスクをGitHub Projectsで可視化」 | 「工夫」「行動」 |
| R | 成果（できれば定量） | result | 「期限内リリース・バグ報告数半減」 | 「成果」 |
| L | 学び | result | 「合意形成には共通の判断基準が要るという学び」 | 「学んだこと」 |
| — | 使った技術・道具 | concept | 「React」「GitHub Projects」 | 「技術」 |

## 必須スロット（欠けたら gap ノードとして立てる）

1. 状況（context）≥1
2. **自分の役割（component）≥1** — 「チームでやりました」で終わる回答は role が gap
3. 障害・対立（problem）≥1 — 困難のない経験談は深掘りに耐えない
4. 行動・工夫（method）≥1
5. 成果（result）≥1 — 定量が無ければ weak を検討

学び（result）は推奨（無ければ立てなくてよい）。

## 粒度規則

- **中心ノード（プロジェクト/経験の場 = context）を必ず立て、ハブにする**。label は会話の呼び方に忠実に。
- **全ノードはハブから到達可能にする**（part_of は子→親向きのため到達性判定では無向扱い）。
  経験中に生じた障害・対立は `ハブ --causes--> problem` で派生させる。
- 束ねノード禁止（研究ドメインと同じ）。行動が複数あれば行動ごとに分ける。
- 技術名の羅列は主要な1〜2個だけノード化。
- 目安 8〜15 ノード（密な会話は〜20 まで許容）。「面接官が深掘りの起点にできる単位か」で判断。

- **成果物（作ったもの）は part_of にしない**: `ハブ --leads_to--> 成果物`（プロジェクトが産物を生む）。
  part_of は役割・目標・工程など「プロジェクトの構成要素」の帰属に限る。
- **チーム共通のツール・慣行はハブから**: Slack・定例MTG・共有ツール等、チーム全体の
  仕組みは `ハブ --uses--> method`。役割ノード（component）から張るのは**本人固有の行動・工夫のみ**。
- **本人は「自分」と表記**: label/detail で本人を指すときは「自分」（「応募者」と書かない。
  アプリではユーザ自身の脳内グラフとして表示されるため）。
- **相手企業は「志望企業」と表記**（「貴社」と書かない。アプリではユーザ視点のグラフになるため。志望動機アンカーは単に「志望動機」）。
- **エッジも節度**: 同一ターゲットへ並列に多数の leads_to を張らない（代表的な因果に絞る）。
  目安: エッジ数 ≦ ノード数 × 1.3。
- **エッジの忠実性**: 関係は会話中で実際に語られた（または質問→回答の対応で裏付く）因果のみ張る。
  「もっともらしい」だけの補完はしない（例: 課題Aと手法Bが両方あっても、A→Bと語られていなければ繋がない）。

## 典型関係パターン

```
component(役割) --part_of-->  context(ハブ)
goal            --part_of-->  context
context(ハブ)   --causes-->   problem(障害・対立)   （経験の中で困難が生じた）
context(ハブ)   --uses-->     method(調査等の起点)
problem(障害)   --leads_to--> method(行動)          （困難がその行動を促した）★v0.1
method          --leads_to-->  result(成果)
result          --leads_to-->  result(学び)
concept(技術)   … method から uses で参照
矛盾（例:「主導した」vs「チームで決めた」）は contradicts で保持
```

※ v0.1: research と同じく「method addresses problem（解決の向き）」はやめ、
**「problem leads_to method（動機づけの向き）」に統一**。同一ペアに両方向は張らない。

## coverage 判定

- **covered**: 役割・行動・結果が具体的（誰に何をして何が起きたか＋できれば数字）
- **weak**: 行動は言えたが自分の寄与や因果が曖昧／数字なし
- **gap**: スロット欠落（特に役割・障害）・名前だけの言及
